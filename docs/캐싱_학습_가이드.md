# 캐싱 코드 학습 가이드

> 이 프로젝트의 Redis ZSET 기반 주문 캐시 구현을 이해하기 위한 학습 로드맵

---

## 1. 왜 캐시가 필요한가? (배경 이해)

### 문제 상황

POS 화면은 주방과 홀 직원이 **실시간으로 계속 새로고침**하며 주문 목록을 확인한다.
요청 한 번에 DB 조회가 발생하고, 1000 TPS 환경에서는 초당 1000번 DB를 때리는 셈.

- DB 조회는 디스크 I/O + 네트워크 + 쿼리 파싱이 동반 → 느리고 비쌈
- Redis는 메모리 기반 → 같은 데이터를 훨씬 빠르게 응답 가능

### 이 프로젝트의 캐싱 목표

> "영업(Sale) 단위로 활성 주문 목록을 Redis에 올려두고, 조회 시 DB 대신 Redis에서 읽는다"

## 2. Redis 핵심 개념 — 코드 이해 전 필수 지식

### 2-1. Redis란?

- **메모리 기반** Key-Value 저장소 (매우 빠름, 보통 DB의 10~100배 속도)
- 데이터는 서버 재시작 시 날아갈 수 있음 (영속성 옵션 별도)
- 캐시, 세션, 실시간 랭킹 등에 자주 사용

### 2-2. Redis 자료구조 — ZSET(Sorted Set)이 핵심

| 자료구조                  | 설명                   | 예시                                   |
|-----------------------|----------------------|--------------------------------------|
| String                | 단순 키-값               | `"user:1" -> "{"name":"홍길동"}"`       |
| Hash                  | 필드-값 묶음              | `"user:1" -> {name: "홍길동", age: 30}` |
| List                  | 순서 있는 목록             | 최근 알림 목록                             |
| **Sorted Set (ZSET)** | **score 기반 정렬된 Set** | **주문 목록 (이 프로젝트)**                   |

#### ZSET이 왜 좋은가?

```
ZSET "sale:1:orders:ORDERED" = {
  "{"orderId":101,...}" -> score: 101.0
  "{"orderId":105,...}" -> score: 105.0
  "{"orderId":110,...}" -> score: 110.0
}
```

- score(숫자)로 자동 정렬됨
- score 범위 조회가 O(log N)으로 빠름
- 이 프로젝트는 **orderId = score** → orderId가 단조 증가하므로 "최근 주문순" 정렬이 자연스럽게 구현됨
- `reverseRangeByScore(0, lastOrderId-1)` → 커서 페이지네이션 구현 가능

### 2-3. TTL (Time To Live)

- Redis 키에 만료 시간을 설정할 수 있음
- 이 프로젝트: `CACHE_TTL = 1시간` → 1시간 후 자동 삭제 (영업 세션 길이에 맞춤)
- 서비스가 꺼지거나 영업 종료 후 메모리 누수 방지

## 3. Spring Data Redis — 사용 방법 이해

### 3-1. ReactiveRedisTemplate이란?

```java
// 동기 버전 (일반적)
RedisTemplate<String, String> redisTemplate;

// 비동기(Reactive) 버전 — 이 프로젝트에서 사용
ReactiveRedisTemplate<String, String> reactiveRedisTemplate;
```

- `Mono<T>`: 결과가 0개 또는 1개인 비동기 스트림
- `Flux<T>`: 결과가 0개 이상인 비동기 스트림
- `.subscribe()`: 비동기로 실행 시작 (결과를 기다리지 않음 = fire-and-forget)
- `.block()`: 비동기 결과를 동기적으로 기다림 (MVC 서블릿 스레드에서 사용)

### 3-2. ZSET 주요 연산

```java
// ZSET에 값 추가: key에 value를 score로 추가
reactiveRedisTemplate.opsForZSet().

add(key, value, score)

// score 범위 내 값을 내림차순으로 조회 (최신순)
reactiveRedisTemplate.

opsForZSet()
    .

reverseRangeByScore(key, Range.closed(0.0, maxScore),Limit.

limit().

count(n))

	// 키 삭제
	reactiveRedisTemplate.

delete(key)

// TTL 설정
reactiveRedisTemplate.

expire(key, Duration.ofHours(1))
```

### 3-3. 직렬화(Serialization)란?

Redis는 바이트(byte)만 저장할 수 있음.
Java 객체 → JSON 문자열 → Redis 저장 = **직렬화**
Redis 꺼내기 → JSON 문자열 → Java 객체 = **역직렬화**

이 프로젝트는 Jackson(ObjectMapper)으로 JSON 변환:

```java
// Java 객체 -> JSON
objectMapper.writeValueAsString(cachedOrder)
// -> '{"orderId":101,"orderStatus":"ORDERED","totalPrice":15000,...}'

// JSON -> Java 객체
objectMapper.

readValue(json, CachedOrderList.CachedOrder .class)
```

## 4. 코드 읽는 순서 (계층별 Bottom-Up)

### Step 1: 도메인 계층 — 캐시에 저장할 데이터 구조

**파일**: `domain/domain-pos/src/main/java/domain/pos/order/entity/vo/CachedOrderList.java`

```
CachedOrderList                  <- 영업 전체 주문 목록 (최상위 래퍼)
  └─ CachedOrder                 <- 주문 1건 (실제 ZSET에 저장되는 단위)
       ├─ orderId                <- ZSET score 원본
       ├─ orderStatus            <- 어느 ZSET 키에 들어갈지 결정
       ├─ totalPrice
       ├─ createdAt
       ├─ CachedTableInfo        <- 테이블 번호
       └─ List<CachedOrderMenu>  <- 주문 메뉴 목록
```

포인트: DB에서 복잡한 Order 엔티티를 조회한 뒤, 캐시에 저장할 **최소 필요 정보만** 담은 경량 VO

---

### Step 2: 도메인 계층 — 캐시 포트 인터페이스

**파일**: `domain/domain-pos/src/main/java/domain/pos/order/repository/SaleOrderCachePort.java`

```java
public interface SaleOrderCachePort {
	void updateCache(Long saleId, List<Order> activeOrders);              // 캐시 갱신

	Optional<List<CachedOrder>> getSaleOrderSlice(...);                   // 캐시 조회

	void evictCache(Long saleId);                                         // 캐시 전체 삭제
}
```

포인트: 도메인은 "캐시가 필요하다"는 것만 알고, Redis라는 구체 기술은 모름.
→ 클린 아키텍처의 **의존성 역전(DIP)**: 인터페이스를 도메인에 두고 구현을 인프라에 둠

### Step 3: 도메인 계층 — 이벤트 기반 캐시 갱신

**파일 1**: `domain/domain-pos/src/main/java/domain/pos/order/event/SaleOrderCacheUpdateEvent.java`

```java
public record SaleOrderCacheUpdateEvent(Long saleId) { ...
}
// "saleId에 해당하는 영업의 캐시를 갱신해야 한다"는 신호
```

**파일 2**: `domain/domain-pos/src/main/java/domain/pos/order/event/SaleOrderCacheProcessor.java`

```java

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)  // 핵심!
public void handleCacheUpdate(SaleOrderCacheUpdateEvent event) {
	List<Order> activeOrders = orderReader.getSaleOrdersWithMenuAndTable(
		event.saleId(), ACTIVE_STATUSES);
	saleOrderCachePort.updateCache(event.saleId(), activeOrders);
}
```

AFTER_COMMIT이 중요한 이유:

```
트랜잭션 시작
  └-> DB에 주문 저장
  └-> 이벤트 발행 (SaleOrderCacheUpdateEvent)
트랜잭션 커밋  <- 이 시점에 DB에 확정
  └-> AFTER_COMMIT -> 리스너 실행 -> DB 재조회 -> Redis 갱신

만약 BEFORE_COMMIT이었다면?
  └-> 트랜잭션 롤백 시 DB는 롤백됐는데 캐시는 이미 갱신 -> 데이터 불일치!
```

### Step 5: 인프라 계층 — Redis 실제 구현

**파일**: `infra/mq/redis-pos/src/main/java/com/pos/cache/RedisSaleOrderCacheAdapter.java`

#### 캐시 키 구조

```
sale:{saleId}:orders:{OrderStatus}

예시:
  sale:1:orders:ORDERED    -> ZSET {score:101 -> "주문JSON", score:105 -> "주문JSON"}
  sale:1:orders:RECEIVED   -> ZSET {score:102 -> "주문JSON"}
  sale:1:orders:COMPLETED  -> ZSET {score:99  -> "주문JSON"}
```

왜 상태별로 분리? → 특정 상태(예: ORDERED만)를 빠르게 조회 가능

#### updateCache 동작 흐름

```
updateCache(saleId=1, orders=[주문A(ORDERED), 주문B(RECEIVED)])

1. 기존 ZSET 키 3개 전부 삭제
   delete "sale:1:orders:ORDERED"
   delete "sale:1:orders:RECEIVED"
   delete "sale:1:orders:COMPLETED"

2. 새 데이터를 상태별로 분류 후 각 ZSET에 저장
   ZADD "sale:1:orders:ORDERED"  score=주문A.orderId  value="주문A JSON"
   ZADD "sale:1:orders:RECEIVED" score=주문B.orderId  value="주문B JSON"

3. 각 ZSET에 TTL 1시간 설정

4. .subscribe() -> 비동기 fire-and-forget (DB 트랜잭션과 무관)
```

선삭제(delete-before-write)가 필요한 이유:

```
주문A가 ORDERED -> RECEIVED로 상태 변경된 경우:

선삭제 없이 그냥 ZADD하면?
  "sale:1:orders:ORDERED" ZSET에 주문A가 아직 남아있음
  "sale:1:orders:RECEIVED" ZSET에도 주문A가 추가됨
  -> 주문A가 두 ZSET에 중복으로 존재 -> 데이터 오염!

선삭제 후 ZADD:
  기존 키 전부 삭제 -> 현재 상태 기준으로 깨끗하게 재작성 -> 정합성 보장
```

#### getSaleOrderSlice 동작 흐름 (캐시 조회)

```
getSaleOrderSlice(saleId=1, statusList=[ORDERED,RECEIVED], pageSize=10, lastOrderId=105)

1. maxScore = 105 - 1 = 104.0

2. ZSET "sale:1:orders:ORDERED"  에서 score 0~104 범위 내림차순 최대 11개 조회
   ZSET "sale:1:orders:RECEIVED" 에서 score 0~104 범위 내림차순 최대 11개 조회

3. 두 결과 합치고 orderId 내림차순 정렬 후 11개(pageSize+1)로 제한

4. 결과가 없으면 Optional.empty() -> 호출 측에서 DB fallback 여부 결정
```

### Step 6: 설정 — ObjectMapper 두 가지 이유

**파일**: `infra/mq/redis-pos/src/main/java/com/pos/global/config/RedisSerializerConfig.java`

| Bean                          | 용도              | 저장 형태              |
|-------------------------------|-----------------|--------------------|
| `zsetObjectMapper`            | ZSET 캐시 직렬화     | 순수 JSON (타입 정보 없음) |
| `jackson2JsonRedisSerializer` | Pub/Sub 메시지 직렬화 | `@class` 필드 포함     |

왜 ZSET은 순수 JSON?

```json
// 순수 JSON (zsetObjectMapper) - 읽기 쉬움
{
  "orderId": 101,
  "orderStatus": "ORDERED",
  "totalPrice": 15000
}

// 타입 정보 포함 (jackson2JsonRedisSerializer)
{
  "@class": "domain.pos.order.entity.vo.CachedOrderList$CachedOrder",
  "orderId": 101,
  ...
}
```

ZSET은 역직렬화 대상 타입(`CachedOrder`)이 고정이라 @class가 불필요하고, 용량 낭비가 됨.

Java Record와 ParameterNamesModule:

```java
// Record는 컴팩트 생성자를 사용
public record CachedOrder(Long orderId, OrderStatus orderStatus, ...) {
}

// 이 모듈이 없으면 Jackson이 파라미터 이름을 못 읽어서 역직렬화 실패
.

registerModule(new ParameterNamesModule())
```

## 5. 전체 흐름 요약

```
[1] 주문 생성 요청
POST /orders
  |
[OrderService.postOrderWithCart()]
  ├─ DB: 주문 저장 (JPA)
  └─ eventPublisher.publishEvent(SaleOrderCacheUpdateEvent.of(saleId))
  |
[트랜잭션 커밋]
  |
[SaleOrderCacheProcessor.handleCacheUpdate()]  <- AFTER_COMMIT 리스너
  ├─ DB: 해당 영업의 활성 주문 전체 재조회 (getSaleOrdersWithMenuAndTable)
  └─ saleOrderCachePort.updateCache(saleId, activeOrders)
       |
   [RedisSaleOrderCacheAdapter.updateCache()]
       ├─ 기존 ZSET 3개 삭제 (ORDERED / RECEIVED / COMPLETED)
       ├─ 새 데이터 상태별 ZSET 저장
       └─ TTL 1시간 설정 (비동기 fire-and-forget)


[2] POS 주문 목록 조회
GET /orders?saleId=1&status=ORDERED
  |
  ├─ [캐시 히트] SaleOrderCachePort.getSaleOrderSlice() -> Redis ZSET 조회 -> 응답
  └─ [캐시 미스] Optional.empty() -> DB fallback (OrderRepository)
```

## 6. 캐싱 전략 — Write-Through

이 프로젝트의 전략:

```
Write-Through: DB 쓰기와 캐시 갱신을 항상 함께 수행

장점: 캐시는 항상 최신 상태 -> 읽기 시 캐시 미스 거의 없음
단점: 쓰기마다 DB 전체 재조회 비용 발생
```

비교:

```
Cache-Aside (Lazy Loading): 읽을 때 캐시 없으면 DB 조회 후 채움
  -> 첫 조회는 느리지만 쓰기 오버헤드 없음

Write-Back: 캐시에만 쓰고 나중에 DB에 반영 (데이터 유실 위험)
```
