# YABAM 기능 개발 워크플로우 (Feature Development Workflow)

이 워크플로우는 `antigravity` 에이전트가 새로운 기능을 기획 및 개발할 때 반드시 따라야 하는 최상위 가이드이자 **지침서**입니다. 모든 파일과 설명은 **한국어**로 작성해야 합니다. 
작업을 수행하면서 필요한 세부 지침은 관련 워크플로우(`@[/...명령어]`)를 꼬리를 물며 탐색해야 합니다.

## 🧭 파생 워크플로우 길라잡이 (Navigation)

개발 도중 아래와 같은 특정 주제의 작업이 조언되거나 필요할 경우, 명시된 워크플로우 경로를 참고하여 규칙을 숙지한 뒤 작업을 진행하세요.
- **아키텍처 및 멀티 모듈 역할과 참조 방향 파악이 필요할 때**: `@[/architecture-overview]`
- **계층(Domain, Infra, API 등)별 개발 패턴 및 객체(Mapper 등) 맵핑 규칙 확인이 필요할 때**: `@[/layer-development-pattern]`
- **기능 개발이나 변경 후 어떻게 테스트 코드를 작성해야 하는지 가이드가 필요할 때**: `@[/testing-strategy]`
- **커밋 메시지 작성 규칙이나 커밋 분리 원칙을 확인할 때**: `@[/commit-convention]`
- **로컬에서 전체 시스템(Config, Discovery, Infra)을 실행하는 절차가 필요할 때**: `@[/local-application-running]`
- **ZSET 캐싱 등 대규모 데이터 부하 테스트(k6)가 필요할 때**: `@[/performance-testing]`
- **🚨 (중요) 새로운 워크플로우 생성 규칙**: 앞으로 사용자가 어시스턴트에게 "새로운 워크플로우를 만들어 주라"라고 지시할 경우, 워크플로우 파일을 생성한 후 **반드시 이 `feature_development` 파일의 "파생 워크플로우 길라잡이" 섹션에도 해당 워크플로우에 대한 설명과 명령어를 추가 업데이트해야 합니다.**

## 🛠️ 개발 프로세스

1. **초기 설계서 작성 (`issue.md`)**
   - 개발을 시작하기 전, `.plan` 폴더 아래에 `issue-{이슈번호}.md` 파일을 생성하여 새로운 기능에 대한 설계를 작성합니다.
   - **이슈 번호 채번:** `origin` 리포지토리에서 가장 최신의 이슈 번호를 확인하고, 바로 다음 번호로 버저닝합니다.
   - **주의:** 초기 설계 단계에서는 절대 `implementation_plan.md`나 `task.md`를 생성하지 마세요.

2. **사용자 컨펌 대기**
   - 사용자(USER)에게 작성한 `issue-{이슈번호}.md` 파일의 설계를 공유하고 통과(승인)를 요청합니다.

3. **이슈 브랜치 생성**
   - 사용자가 설계(`issue.md`)를 확인하고 개발을 승인하면, 해당 이슈 번호를 바탕으로 이슈 브랜치를 생성합니다. (예: `git checkout -b feature/issue-N-title`)

4. **구현 계획서 작성 (`task.md` 및 `implementation_plan.md`)**
   - 브랜치 생성 후, 기능 구현을 안내하기 위한 계획서인 `task_{이슈번호}_{제목}.md`와 `implementation_plan_{이슈번호}_{제목}.md`를 `.plan` 디렉터리 내에 생성합니다.
   - 이 파일들은 기능 정의(명세) 목적이 아니며, 이미 승인된 `issue.md` 설계를 바탕으로 **어떻게(how) 코드로 구현할지**에 대한 체계적이고 세부적인 구현 계획서 역할을 수행합니다.

5. **코드 작성 및 특정 행동 지침 참고**
   - 구현 중 아키텍처나 코딩 컨벤션에 대해서는 `@[/layer-development-pattern]` 등을 참고하고, `.skil/` 디렉터리의 `.md` 지침들 또한 반드시 숙지합니다.
   - 계획된 순서대로 코드 수정 및 기능 개발을 진행합니다.

6. **✅ 필수 검증 사항 (테스트 코드 원칙)**
   - **어떤 형태의 코드를 수정하거나(기능 개발, 리팩터링, 새 기능 추가 등) 기여하든 예외 없이 반드시 관련된 통합 및 단위 파트의 Test를 작성해야만 합니다.**
   - 코드 수정 작업 이후에는 반드시 `@[/testing-strategy]` 워크플로우를 참고하여 계층의 규칙에 맞게 테스트 코드를 설계 및 작성하십시오.
   - 작성한 테스트가 로컬이나 빌드 환경에서 완전히 성공(`PASS`)하는지 **검증 과정을 거치고 통과 내역을 확인받아야** 비로소 작업이 완료된 것으로 간주됩니다.
